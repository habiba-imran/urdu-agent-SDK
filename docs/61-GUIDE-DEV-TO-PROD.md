# 61-GUIDE-DEV-TO-PROD.md — every change needed to flip from dev to prod

P8-T05. Written from the actual code/config surface (`.env.example`, `config.py`,
`worker/factories.py`, `docs/41-HUMAN-TASKS.md` H1), not a generic checklist. Every line below
is either a confirmed env-var read or an explicit doc/ADR reference.

## 2. Everything else that needs a look, confirmed by reading the actual code

- **`ADMIN_JWT_SECRET`** — currently auto-generated by `admin/app.py::_ensure_admin_jwt_secret()`
  if absent (a Phase 6 judgment call, `state/HANDOFF.md` §5 item 2). For prod, generate and set
  this deliberately rather than letting the first prod process run auto-generate it — same value
  needs to persist across restarts/deploys, and an auto-generated one living only in a
  process-local `.env.local` write would not survive a redeploy to a fresh environment.
- **`ADMIN_PORTAL_ORIGINS`** — defaults to `http://localhost:5173` if unset (`admin/app.py`).
  **Must be set to the real prod admin-portal origin before shipping** — the default is a dev
  placeholder and GATE 6 line 4 (admin portal not reachable from the SDK's origin) depends on
  this allowlist being correct, not just non-empty.
- **`RATE_LIMIT_PER_MIN`** — NOT an env var, a hardcoded constant in `control_plane/app.py`
  (`= 120`, confirmed deliberate per ADR-023). Changing it for prod (if 120/tenant/minute isn't
  the right prod value) requires a code change + a new ADR entry, not a config flip.
- **`tenants.max_concurrent` / `max_minutes_month`** — per-tenant DB values, not global config.
  Confirm whatever provisioning flow creates prod tenants sets sane real values — dev's test
  tenants have used values like `20` or `100000` deliberately to bypass quota during testing
  (e.g. `scripts/verify_rate_limit_live.py`); those are NOT prod-appropriate defaults.
- **`UPLIFT_VOICE_ID`** default (`v_meklc281`, `config.py:20`) is this project's own demo voice —
  confirm real tenant agents are always created with a real `voices.id` from the picker catalogue,
  not silently falling back to the demo default in prod.
- **`LLM_MODE`** in `.env.example` — confirmed vestigial (see the fix landed alongside this doc):
  not read by `worker/` or `config.py` at all, only by the old CER-harness's offline guard
  (`tests/conftest.py`). Irrelevant to what the real worker does in prod either way.

## 3. What does NOT change

- The SDK bundle (`sdk/dist/`) — GATE 4 already confirmed it holds zero secrets and never
  references admin/. No prod-specific rebuild is implied by any of the above; the same bundle
  works against dev or prod because it only ever talks to the host platform's own
  `sessionEndpoint`, never a provider directly.
- `control_plane/mint.py`'s logic — HMAC verify, replay window, quota checks, JWT minting are all
  environment-agnostic; only the DB/LiveKit credentials they operate against change.
- RLS policies — table-level, defined in migrations, identical in dev and prod once
  `supabase/migrations/` is applied to `uva-prod` the same way it was applied to `uva-dev`.

## 4. Rollback

See `docs/28-PHASE-8-PROD-READY.md` P8-T06 / GATE 8: every phase gate is tagged
(`p0-gate-pass` through `p7-gate-pass`, created and rollback-tested this session — see
`state/PROGRESS.md`). Reverting a bad prod flip means `git checkout <tag>` to the last-known-good
phase state, not just flipping the switches above back — a code rollback and a config rollback
are two different operations and both may be needed depending on what broke.

## 5. What this doc does NOT cover

Actually executing any of the above (funding Soniox, upgrading the LiveKit plan, creating/
switching to the `uva-prod` Supabase project, merging to `main`) — all of that is human-only work
per `docs/41-HUMAN-TASKS.md` and GATE 8's own human-gate line ("you merge to main. The agent
never merges."). This document exists so that work is a checklist, not a rediscovery.
